## 1. Краткое вступление

Satisfactory Task Manager — микросервисное веб-приложение на **Go** для координации производственных задач в кооперативной игре **Satisfactory**.

Пользователь через русскоязычный веб-интерфейс:
- регистрируется и входит в систему;
- создаёт задачи с привязкой к рецептам игры;
- назначает исполнителей;
- видит расчёт производственного плана;
- отслеживает статусы: `pending` → `in_progress` → `completed`.

Технически система состоит из **пяти сервисов на Go**, общей **PostgreSQL**, балансировщика **NGINX** (3 реплики task-service), кэша **Redis**, очереди **RabbitMQ** с фоновым **task-worker**, а также **Prometheus** и **Grafana**. Всё упаковано в **Docker Compose**.

### Роли компонентов

| Компонент | Зачем |
|-----------|--------|
| **gateway** | Единая точка входа для браузера: HTML, HTMX, cookie→JWT, расчёт плана производства |
| **user-service** | Регистрация, логин, выдача JWT, поиск пользователей |
| **task-service** | CRUD задач, кэш Redis, публикация событий в RabbitMQ |
| **data-service** | Справочник рецептов Satisfactory из `game-data.json` |
| **task-worker** | Асинхронная обработка событий: лог + инвалидация и прогрев кэша |
| **NGINX** | Балансировка 3 реплик task-service (round-robin) |
| **Redis** | Общий кэш JSON-ответов `GET /tasks` для всех реплик |
| **RabbitMQ** | Развязка записи задачи и фонового обновления кэша |

### Паттерн BFF (Backend For Frontend)

Gateway — не просто прокси. Он:
- рендерит HTML-шаблоны;
- переводит cookie `token` в заголовок `Authorization: Bearer` для внутренних API;
- обогащает задачи данными из data-service (иконки, названия рецептов);
- выполняет расчёт производственного плана (модуль `production/`).

Микросервисы task-service и user-service отдают **JSON**, браузер работает только с gateway.

### 4.3. Task-service

**Точка входа:** `services/task-service/cmd/main.go`  
**Порт:** 8082 (3 контейнера: `task-service-1/2/3`)  
**Переменная:** `INSTANCE_ID=tasks-1` (и tasks-2, tasks-3) — попадает в заголовок ответа

**API (все с JWT middleware):**

| Маршрут | Обработчик | Назначение |
|---------|------------|------------|
| `POST /tasks` | `CreateTask` | Создание задачи |

- `handlers/task.go` — HTTP-логика

**Точка входа:** `services/satisfactory-data-service/cmd/main.go`  
**Порт:** 8083

**Назначение:** при старте импортирует `data/game-data.json` (формат SatisfactoryTools / greeny) в PostgreSQL. Отдаёт REST API для gateway.

**Основные маршруты:**
- `GET /api/recipes/search?q=` — поиск рецепта по имени
- `GET /api/recipes/{className}` — полный рецепт (ингредиенты, продукты, длительность)

**Модель рецепта** (`internal/models/recipe.go`):
- `ClassName`, `DisplayName`, `Duration`

### 4.5. Task-worker

**Точка входа:** `services/task-worker/cmd/main.go`  
**HTTP нет** — только потребитель RabbitMQ.

**Файл:** `internal/consumer/consumer.go`

**Логика:**
1. Подписка на exchange `task.events` (тип **fanout**)
2. Очередь `task.worker`
3. На сообщение `task.created` / `task.updated` / `task.deleted`:
   - запись в лог (audit);
   - `cache.InvalidateLists(...)` — сброс ключей Redis;
   - `warmLists(...)` — повторное чтение из Postgres и запись в Redis.

**Зачем:** после изменения задачи кэш не остаётся пустым долго — worker сразу прогревает его, следующие запросы получают `X-Cache: HIT`.

## 5. Сценарии: как идёт запрос

### 5.1. Регистрация и вход

```
1. Браузер: GET /register → gateway отдаёт register.html
2. Браузер: POST /register (form) → gateway AuthHandler.Register
3. Gateway → POST user-service:8081/api/register (JSON)
4. user-service: UserRepository.Create → bcrypt hash → INSERT users
5. jwt.GenerateToken(userID) → ответ { token, user }
6. Gateway: Set-Cookie token=... → redirect /
```

**При логине** — то же, но `POST /api/login`, проверка пароля через `CheckPassword`.

**Важно:** JWT подписан секретом `JWT_SECRET` (одинаковым в user-service и task-service). Gateway хранит токен в **HttpOnly cookie**, task-service получает его как `Authorization: Bearer <token>`.

---

### 5.2. Создание задачи

```
1. Пользователь на главной: вводит рецепт (HTMX GET /recipes/search)
2. data-service возвращает список рецептов
3. POST /tasks (форма, hx-post) → gateway TaskHandler.CreateTask
4. Gateway проверяет tier HUB через data-service (unlock)
5. TaskClient.CreateTask → POST http://nginx:8090/tasks + Bearer JWT
6. NGINX → round-robin → task-service-N
7. task-service CreateTask:
   - status = "pending"
   - TaskRepository.Create → INSERT tasks
   - invalidateAfterChange() → Redis DEL
   - publishEvent("task.created") → RabbitMQ
8. Ответ 201 JSON → gateway
9. Gateway вызывает GetTasks → рендер tasks.html (HTMX подменяет #tasks-list)
10. task-worker асинхронно: invalidate + warm cache
```

---

### 5.3. Получение списка задач (кэш + балансировка)

```
1. HTMX: GET /tasks?scope=all|mine|completed
2. gateway TaskHandler.GetTasks:
   - читает cookie token
   - TaskClient.GetTasks → GET nginx:8090/tasks?scope=...
3. NGINX → одна из реплик task-service
4. task-service GetTasks:
   a) cache.Get(scope, userID) → HIT: вернуть JSON, X-Cache: HIT
   b) MISS: SELECT из Postgres → cache.Set → X-Cache: MISS
5. Заголовок X-Instance-ID: tasks-1|2|3 (из env INSTANCE_ID)
6. gateway пробрасывает X-Instance-ID и X-Cache в ответ браузеру
7. gateway enrichTask() — подтягивает иконки/названия из data-service
8. рендер HTML-фрагмента tasks.html
```

**Scope:**
| scope | SQL / смысл |
|-------|-------------|
| `all` (по умолчанию) | Активные задачи команды |
| `mine` | Назначенные текущему пользователю, не completed |
| `completed` | Выполненные |

---

### 5.4. Смена статуса задачи

```
POST /tasks/status/{id}  (form: status=in_progress|completed)
→ gateway UpdateTaskStatus
→ TaskClient.UpdateTask → PATCH nginx:8090/tasks/{id}
→ task-service: UPDATE tasks SET status=...
→ invalidate + publish task.updated
→ worker прогревает кэш
```

Диаграмма состояний: `pending` → `in_progress` → `completed`.

## 6. NGINX и горизонтальное масштабирование

**Файл:** `nginx.conf`

```nginx
upstream task_backend {
    server task-service-1:8082 resolve max_fails=2 fail_timeout=5s;
    server task-service-2:8082 resolve ...;
    server task-service-3:8082 resolve ...;
}
```

- **Алгоритм:** round-robin (по умолчанию в NGINX)
- **`resolve`** — динамическое обновление IP контейнеров Docker (без этого после пересоздания контейнеров бывает 502)
- **`proxy_pass_header`** — пробрасывает `X-Instance-ID` и `X-Cache` клиенту

**Как доказать:**
- DevTools → Network → запрос `tasks` → Response Headers
- Или нагрузочный тест: `loadtest/loadtest.go` — ~33% запросов на каждую реплику

**Почему 3 реплики:** горизонтальное масштабирование stateless HTTP-сервиса; состояние в Postgres и Redis, не в памяти реплики.

## 7. Redis-кэш

**Файл:** `services/task-service/internal/cache/task_cache.go`

**Ключи:**

| Scope | Ключ Redis |
|-------|------------|
| Все активные | `tasks:list:all` |
| Свои | `tasks:list:mine:{userID}` |
| Выполненные | `tasks:list:completed` |

**TTL:** 60 секунд (`REDIS_CACHE_TTL`)

**Логика GetTasks:**
```go
if body, hit := h.cache.Get(scope, userID); hit {
    w.Header().Set("X-Cache", "HIT")
    w.Write(body)
    return
}
// ... запрос в БД ...
h.cache.Set(scope, userID, body)
w.Header().Set("X-Cache", "MISS")
```

**Инвалидация** (`InvalidateLists`):
- всегда удаляет `tasks:list:all` и `tasks:list:completed`
- плюс `tasks:list:mine:{id}` для затронутых исполнителей

**Кто инвалидирует:**
1. **task-service** — синхронно при create/update/delete
2. **task-worker** — при событии из RabbitMQ, затем прогрев

**Почему Redis общий:** все 3 реплики читают один кэш — после HIT на любой реплике данные актуальны (после инвалидации worker их обновляет).

## 8. RabbitMQ и task-worker

**Публикация** (`task-service/internal/messaging/publisher.go`):
- Exchange: `task.events`, тип **fanout**
- События: `task.created`, `task.updated`, `task.deleted`
- Тело: JSON с `task_id`, `user_id`, `status`, `assigned_to_user_id`

**Потребление** (`task-worker/internal/consumer/consumer.go`):
- Очередь `task.worker`, привязана к fanout
- `handle()` → лог + `InvalidateLists` + `warmLists`

**Зачем очередь:**
- не блокировать HTTP-ответ при прогреве кэша;
- возможность добавить других подписчиков (email, аналитика);
- разделение ответственности (task-service пишет, worker обслуживает кэш).

**Проверка на защите:**
```bash
docker logs task-worker --tail 30
# после создания задачи — сообщение [audit] task.created
```

## 9. Gateway: UI, HTMX, калькулятор

### HTMX

Библиотека подключается в шаблонах. Примеры:
- `hx-post="/tasks"` — создание задачи без перезагрузки страницы
- `hx-get="/tasks?scope=mine"` — подгрузка списка в `#tasks-list`
- `hx-get="/tasks/detail/{id}"` — карточка задачи в `#task-detail`
- `hx-get="/recipes/search"` — автодополнение при вводе рецепта

**Файлы:** `templates/index.html`, `tasks.html`, `scripts_tasks.html`

### Калькулятор производства

**Не отдельный микросервис** — логика в gateway:

| Файл | Назначение |
|------|------------|
| `internal/production/calc.go` | `ItemsPerMinute`, `ClockPercent` (энергомодули) |
| `internal/production/plan.go` | `StepPlan` — план на один шаг цепочки |
| `internal/production/factory.go` | Агрегация цепочки рецептов |
| `internal/handlers/production.go` | `planForTaskRecipe`, построение плана |
| `handlers/tasks.go` | `GetTaskProduction`, `buildTaskProduction` |

**Входные данные:** рецепт из data-service, целевая производительность (предметов/мин), tier HUB, шарды, уровень конвейера/трубы.

**Выход:** HTML с таблицей машин, скоростей, энергопотребления (`task_production.html`).

## 14. Вопросы преподавателя и ответы

### Общие

**Почему микросервисы, а не один монолит?**  
Задачи масштабируются отдельно (3 реплики), auth и справочник рецептов изолированы. Можно обновлять gateway без перезапуска task-service.

**Почему Go?**  
Встроенный `net/http`, статическая типизация, быстрая сборка, один бинарник в Docker-образе, хорошо подходит для REST-микросервисов.

**Где хранятся данные?**  
PostgreSQL: пользователи, задачи, рецепты. Redis — только кэш (временный). RabbitMQ — очередь сообщений (не БД).

### Безопасность

**Как защищены API task-service?**  
Middleware проверяет JWT из заголовка `Authorization`. Без валидного токена — 401.

**Где пароль пользователя?**  
В Postgres в виде bcrypt-хеша. В JSON наружу не отдаётся (`json:"-"`).

**Почему cookie, а не localStorage?**  
Gateway ставит HttpOnly cookie — JS на странице не читает токен (защита от XSS).

### Производительность

**Зачем Redis?**  
`GET /tasks` частый запрос; кэш снимает нагрузку с Postgres и ускоряет ответ (HIT ~миллисекунды).

**Зачем 3 реплики?**  
Распределение нагрузки (NGINX round-robin), отказоустойчивость (max_fails).

**Что если Redis упадёт?**  
`TaskListCache` при недоступности Redis отключается (`enabled=false`), запросы идут в БД — система работает, но медленнее.

### Архитектура

**Чем gateway отличается от task-service?**  
Gateway — HTML + оркестрация + калькулятор. Task-service — чистый REST API + персистентность + кэш + события.

**Зачем RabbitMQ, если кэш сбрасывается в task-service?**  
Task-service сбрасывает кэш синхронно; worker **прогревает** его асинхронно и ведёт audit. Плюс расширяемость (новые подписчики).

**Почему fanout, а не direct queue?**  
Fanout рассылает событие всем очередям-подписчикам; можно добавить второй worker без смены publisher.

### Предметная область

**Откуда рецепты Satisfactory?**  
Файл `game-data.json` (формат SatisfactoryTools), импорт в Postgres при старте data-service.

**Что такое ProductionPlan?**  
Расчёт цепочки: какие здания, сколько, с какой скоростью, чтобы произвести N предметов в минуту с учётом энергомодулей и tier HUB.

### Docker / деплой

**Почему на VPS Grafana не открывается по IP?**  
В `docker-compose.vps.yml` порт привязан к `127.0.0.1:3001` — только localhost. Доступ через SSH-туннель (безопасность).

**Что делает Caddy?**  
Терминирует HTTPS на порту 8080, проксирует на gateway.
